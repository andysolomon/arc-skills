# Salesforce engineering

Work in an org is source in a Salesforce DX project: every change is a file in `force-app`, retrieved before it is edited and deployed by the `sf` CLI. A builder (Lightning App Builder, Flow Builder) is fine in a scratch org or sandbox when its result is retrieved as source; nothing is clicked together in production. [template/](template) is a small working project in that shape: an `accountList` component with every state and its Jest tests, Apex behind it with its tests, a permission set, the org's token module, and the checks. Start from it for a new project.

`sf` below means `npx -y @salesforce/cli@2.159.7` (see Pins).

## Steps

1. **Pick the rung.** Choose the lowest one that serves the request, and say which in one line.
   - Configuration only (a field, a list view, a validation rule, a page layout, a permission set): metadata, no code.
   - Automation: a record-triggered Flow when the logic is a few field updates an admin will maintain; Apex when it needs bulk work over many records, callouts, real branching, or tests that pin the behaviour.
   - A screen: a Lightning Web Component on a Lightning page.
   - A web app outside the org that reads org data is not this skill: use `arc-web-production`, with `arc-sf-jwt-bearer` for the server-to-server sign-in.

   Completion: the rung and its reason are stated.
2. **Find the org and start from a passing baseline.** `sf org list` names the target alias. Find its type by querying, not guessing: `sf data query --query "SELECT IsSandbox, OrganizationType FROM Organization" --target-org <alias>` (scratch orgs also show in `sf org list` as scratch). Production is never the place to develop or try things: if it is the only org, say so and stop.
   - **New project:** `cp -R <skill-dir>/template/. <dir>` (the `/.` keeps the dot files), then rename `name` in `package.json` and `sfdx-project.json`. Delete the example (`accountList`, the three classes, `Account_List_User`) once your own work replaces it. Set `sourceApiVersion` to the org's API version (`sf org display`). Baseline: `npm ci` and `npm run check`.
   - **Existing project:** the baseline is the project's own checks (its `npm test`, lint, whatever it has), run before you add anything. Then, for a first screen, bring over from the template: `scripts/check-styles.mjs`, `scripts/sync-tokens.mjs`, `jest.config.js` (merge its `moduleNameMapper` line into an existing one), `lwc/arcTokens`, `.prettierrc`, the `.forceignore` lines, and the `devDependencies` and scripts in `package.json`. Run the style lint only on the components you add or change (`node scripts/check-styles.mjs <file.css> ...`); existing components keep their own look until a restyle is asked for.

   Completion: the target alias and its queried type are stated, and the baseline passes before you change anything. If it doesn't, stop and report that.
3. **Retrieve before you change.** For every existing component you will touch, run `sf project retrieve start --metadata <Type:Name> --target-org <alias>`, then `git diff`. The org is the truth; never edit from memory of what it holds. Completion: each touched component's local source matches the org before your edit, or the reply names the difference.
4. **Design access before code.** List every object and field the change reads or writes, and the permission set that grants each. Grant through permission sets, one per job, never by editing a profile. Completion: the list exists, and every entry has a permission set in `force-app`.
5. **Write the change.** Read [references/code-rules.md](references/code-rules.md) now: it holds the rules for Apex, triggers, Flows, components on record pages, and the pitfalls. Completion: Apex runs as the user (`with sharing`, `WITH USER_MODE`), has no query or DML inside a loop, and turns every failure at an `@AuraEnabled` boundary into an `AuraHandledException` with a sentence; every component state renders something specific.
6. **Apply the look** (screens only). Do `arc-design`'s steps 3 and 4 (apply the look, check the taste and motion rules), not its step 1, which routes you back here. The org's tokens live in `lwc/arcTokens`, generated by `node scripts/sync-tokens.mjs <arc-design>/tokens.css`: arc-design's host exception (light values, Salesforce blue accent). Never edit that file by hand. Every component stylesheet starts with `@import 'c/arcTokens';`. Controls are base components (`lightning-button`, `lightning-input`), which carry the host's keyboard and screen-reader behaviour; our own markup uses the tokens. Completion: the style lint passes for every new or changed stylesheet, and `node scripts/sync-tokens.mjs <arc-design>/tokens.css --check` passes.
7. **Test without an org.** Jest for every component state (Apex is mocked with `createApexTestWireAdapter`), an Apex test class for every class. Completion: `npm run check` passes (Jest, style lint, Apex syntax and format, offline conversion to Metadata API format), and one expectation was changed to a wrong value, seen to fail, and restored.
8. **Test in an org.** Read [references/org-work.md](references/org-work.md) for scratch orgs, sandboxes, Lightning pages and data. Deploy only the paths you changed, assign the permission set to a test user, and run your test classes. Look at the screen as that user, at desktop width and in the Salesforce mobile app or a 390 px window, in every state. Completion: your Apex tests pass, each new or changed class is at least 85% covered, and the screen checks are done, or the reply says `NOT_RUN` for each with the reason (no org, no Dev Hub).
9. **Deploy to production only when asked**, by org-work.md's Production steps: confirm, validate, quick-deploy, and a separate confirmation for any deletion. Completion: the deploy ID, the test result and the rollback (the retrieved source from step 3) are in the reply.
10. **Report** through `arc-html-response`, ending with its packet. Completion: every check is labelled `PASS`, `FAIL` or `NOT_RUN`.

## Pins

`package-lock.json` pins every version; install with `npm ci` and commit the lockfile. `@salesforce/sfdx-lwc-jest` is 7.9.0, `prettier` 3.10.1 with `prettier-plugin-apex` 2.4.0. The `sf` CLI runs through `npx -y @salesforce/cli@2.159.7`, not as a dependency: with it in the tree, npm writes a lockfile that `npm ci` then rejects. A global `sf` works too, but say its version. Don't raise a pin as a side effect of other work.

## Maintaining this skill

After changing the template, run `bash <skill-dir>/tests/test-template.sh`. It copies the template to a temp folder and runs `npm ci`, the Jest tests, a wrong expectation that must fail, the style lint, the Apex check, the offline conversion and the token check against `arc-design`. It needs the network and no org; the Apex tests and a deploy validation need one, so run those by hand against a scratch org before a release.
