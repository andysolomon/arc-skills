# 3D

A scene here is one `<canvas>` inside a Foldkit view. A Mount builds the three.js renderer when the canvas enters the page and disposes it when the canvas leaves. The Model stays the only state. It says what the scene should show, and Commands carry each change to the running scene. Everything a person reads is HTML around the canvas.

This skill builds level 5 of `arc-design`'s pyramid and starts from `arc-web-production`'s template. [overlay/](overlay) is a working example on the template's notes app: one bar per note, placed by the order the notes were written, sized by their length, in a lane that says whether the server has them. Copy from it. Its data is thin on purpose, so it shows the wiring, not a case for 3D.

## Steps

1. **Decide that it is level 5.** A scene earns the GPU when the data has three dimensions, when the thing is a solid or a space (a part, a room, a terrain, a network laid out in depth), or when SVG was tried and measured too slow for the number of marks. A chart that fits in SVG stays in SVG, at level 1 or 2. A scene that shows no data and no mechanism is decoration. Say so and don't build it. Completion: one sentence names what the scene shows from the Model and why SVG can't show it.
2. **Start from a passing baseline.** Do `arc-web-production`'s steps 1 and 2 for the app, then `bash <skill-dir>/scripts/apply-overlay.sh <app-dir>`. It copies the overlay, installs the pinned packages and adds the npm scripts. It replaces one template file, `src/entry.ts`, and leaves a changed one alone. Completion: `npm run check` passes before you change anything.
3. **Design the states and the data path before the scene.** Read [references/scene-rules.md](references/scene-rules.md) now. It holds the file shape, the Mount lifecycle, the token mapping, the render loop, every state's screen, and the pitfalls. Write what the scene draws as plain values first (`src/scene/data.ts`). Completion: the scene's status is a tagged union with a screen for each case, the Mount's args are named `initial…`, and every Message that changes the picture leaves `update` with a Command.
4. **Get the geometry.** Build it in code (boxes, lines, instanced meshes), as the overlay does. That is the default and it needs no file. For a shape code can't make, a model comes from Blender. If the `blender-skills` plugin and Blender 5.2 or later are installed, follow [references/blender-models.md](references/blender-models.md). If either is missing, say so and stay with geometry built in code. Never download a stock model. Completion: the reply names where each shape comes from, and a model file, if any, is under its size budget.
5. **Build the scene** in `src/scene/scene.ts`, the only file that imports `three`. Import the names the scene uses. Build every GPU resource in `startScene` and free every one in `dispose`. Render on demand. Completion: `npm run lint:scene` passes.
6. **Apply the look.** Read `arc-design`'s "The look", "Taste rules" and "Motion" sections and follow them; don't run its routing steps, which send you back here. The scene's colours and timings come from the tokens through `src/scene/tokens.ts`, at mount and again when the colour scheme changes. No scene file names a colour. Text stays HTML, never canvas text. Under `prefers-reduced-motion: reduce` a change is one frame. Completion: `npm run lint:styles` and `npm run lint:scene` pass.
7. **Test without a browser.** Story tests for `update` (each change to the picture is a Command), Scene tests that the Mount is present and that each state renders its screen. Completion: `npm run check` passes, and one wrong expectation, in a temporary copy of a test file, was seen to fail.
8. **Test in a real browser.** `npm install --save-exact --save-dev playwright-core@1.65.1`, then run `test/scene.browser.mjs` as its header says, against the built app and the mock API. Adapt its expectations to your scene. Completion: it passes, or the reply says `NOT_RUN` and why. It must show non-blank pixels, token colours in both colour schemes, a Model change that changes the picture, the fallback, and disposal on leaving.
9. **Look at the picture.** Follow [references/visual-check.md](references/visual-check.md). Take a screenshot of the running scene, compare it with a written target, fix what differs, and repeat until its stop condition. If the `dream-loop` skill, an image tool and a subagent are available, use them as that file says. If one is missing, say which and do the written-target loop. Completion: the last round's verdict is in the reply, with the screenshot's width and colour scheme.
10. **Send frame-rate work to `arc-webgl-performance`.** Headless Chromium draws WebGL in software, so the browser test proves the scene draws, reacts and cleans up. It does not prove frame rate. Completion: every frame-rate claim names the hardware it was measured on, or is `NOT_RUN`.
11. **Report** through `arc-html-response`, ending with its packet. Completion: every check is labelled `PASS`, `FAIL` or `NOT_RUN`, and Blender, image generation and frame rate each have a label.

## Pins

`scripts/apply-overlay.sh` holds the versions. `three` is 0.187.0, pinned exactly, because three.js ships breaking changes in minor releases and has no stable major. `@types/three` is 0.187.0, the same release, because the types are a separate package and must match. `playwright-core` is 1.65.1 for the browser test, installed only when that test runs; it drives a browser you already have through `CHROME_PATH`. Don't raise a pin as a side effect of other work, and never raise one of the template's pins.

## Maintaining this skill

After changing the overlay, or after the template changes, run `TMPDIR=<a folder with room> bash <skill-dir>/tests/test-overlay.sh`. It copies the current template, applies the overlay, and runs typecheck, tests, both lints, the build and the browser test, plus three checks that a wrong value fails. It needs the network and prints `SKIP` for the browser step when no Chromium is found. The Blender path, the image tool and frame rate are not covered by it. Each reference says what was `NOT_RUN`.
