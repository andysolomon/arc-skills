# Web production

A web app here is a Foldkit program: one Model, Messages as facts, a pure `update`, a pure `view`, and side effects as Commands. [template/](template) is a small working app in that shape: a notes list with its tests, a mock API, a static render, a style lint, an API check and a Cloudflare stack. Start from it; don't start from a blank folder or from React.

This skill builds level 2 of `arc-design`'s pyramid, an app. The levels above it start from the same template and add to it: `arc-interaction` for gestures and springs (level 3), `arc-realtime` for live connections (level 4), `arc-3d` for scenes on the GPU (level 5). Load the one the request needs after step 2.

## Steps

1. **Pick the rung.** Choose the lowest one that serves the request, and say which in one line.
   - Nobody types into it: render a pure view once to a page with no script (`npm run static`), then publish it by `arc-html-response`'s rules.
   - People type into it, but it is a throwaway or a quick try: a Lakebed capsule. Follow `arc-html-response`'s `lakebed.md`, not this skill.
   - It must last, needs npm packages, or needs its own domain: a Foldkit app. Continue below.

   Completion: the rung and its reason are stated.
2. **Start from a passing baseline.**
   - **New app:** `cp -R <skill-dir>/template/. <app-dir>` (the `/.` keeps `.gitignore` and `.github/`), then `git init` there so the lockfile and the work have a history. The copied `.github/workflows/ci.yml` checks the app on GitHub and never deploys; it assumes the app is the repo's root.
   - **Existing app** in this shape: don't copy anything.
   - Then `npm ci` (or `npm install` for an existing app without a lockfile) and `npm run check`. The install is about 650 MB, mostly workerd and Alchemy. npm may warn that `workerd`'s install script is "not yet covered by allowScripts"; that is expected and harmless.

   - **Then rename, after the baseline passes:** `name` in `package.json` (then `npm install --package-lock-only`, which rewrites it in the lockfile), `<title>` in `index.html`, the stack name `"FoldkitApp"` in `cloudflare/alchemy.run.ts`, and the `Notes` class and `NOTES` binding in `cloudflare/worker.ts` and `alchemy.run.ts`. The `/api/notes` route is named in `worker.ts`, `scripts/mock-api.ts`, `scripts/api-check.ts`, `scripts/render-static.ts`, `src/commands.ts` and `.github/workflows/ci.yml`: change them together in step 5.

   Completion: `npm run check` passes on the untouched copy, before any rename or change. If it doesn't, stop and report that. One exception: an app that came for a restyle may fail only `npm run lint:styles`. Then the baseline is `npm run typecheck && npm test`, and step 7 fixes the lint.
3. **A restyle stops here and jumps to step 7.** A restyle changes only `src/tokens.css` and `src/styles.css`, plus the font bundle when the app lacks it: `src/fonts.css`, `src/fonts/` and its `<link>` in `index.html`, copied from the template. Screen text and behaviour are a separate request. Completion: the reply says the request is a restyle, or that it isn't.
4. **Design the states before the screen.** Write the Model and Messages first. Read [references/foldkit-rules.md](references/foldkit-rules.md) now: it holds the rules for Model, `update`, Commands, `view`, tests, and the pitfalls. Completion: every remote value is an `AsyncData`, every write the user can start has a phase union and an idempotency key, and every Message is a past-tense fact.
5. **Write the API.** Change `cloudflare/worker.ts` and mirror the change in `scripts/mock-api.ts`; the two must keep the same contract. Every write is idempotent on its key: a repeat stores nothing new and answers 200. Validate input and answer 400, with the same limits in the Worker and the mock, and a check for each limit in `api-check.ts`. Update `scripts/api-check.ts` for the new routes, and when you rename the Model, rename `scripts/render-static.ts`'s import and view too (or delete that file, the `static` script and the `npm run static` line in `.github/workflows/ci.yml` if the app will never need a static page). Completion: `npm run api:check -- <url>` passes against the mock (`npm run mock`) and against the Worker (`npm run cf:dev`). Stop `cf:dev` the way step 9 says: SIGINT to its whole process group, then wait for the port to close.
6. **Write `update`, the Commands and `view`.** Completion: `update` reads no clock, randomness or network; every Command turns its failures into a Message; loading, empty, failure and stale each render something specific; every control has a label; lists are keyed by a Model identity.
7. **Apply the look.** Read `arc-design`'s "The look", "Taste rules" and "Motion" sections and follow them, then run the reviews its step 4 names (`reviews.md`) that are installed; don't run its routing steps, which send you back here. `src/tokens.css` is a byte-for-byte copy of `arc-design/tokens.css`; app-specific extra tokens go at the top of `src/styles.css`, never in the copy. `src/fonts.css` bundles Geist and Geist Mono from `src/fonts/`, so the app shows the same type on every machine; the style lint allows no other `@font-face`. Each animated state gets its own `@keyframes` name: a class change restarts an animation only when its name changes, so one shared name plays once and never again. When the token check fails on an older copy, copy `tokens.css` again. Completion: `npm run lint:styles` passes (tokens only, motion guarded, one keyframes name per state), `node <arc-design>/scripts/check-tokens.mjs src/tokens.css` passes, and each of `arc-design`'s taste rules holds or is named as not holding. The lint can't see a 32 px button or a missing label.
8. **Test without a browser.** Story for `update`, Scene for `view`, a direct `update` call for anything with two requests in flight, and a Command test with a stub client for each new Command. Add tests for each new write: the key comes from the Model, a double submit sends nothing, a retry reuses the key. Completion: `npm run check` passes, and one deliberately wrong expectation, in a temporary copy of a test file, was seen to fail. For a restyle, `npm run check` only proves behaviour didn't change and the wrong-expectation check isn't needed; step 9 proves the look.
9. **Look at it.** Run the app at 390 px and at desktop width, in light and dark, and put it in every state: loading, empty, loaded, stale, failed to load, and for each write its saving, saved, lost-reply and failed cases. A new write needs its own mock switch for its failure, in the style of `FAIL_SAVES`. Use any browser you have (headless Chromium driven by Playwright works). Free ports first (`ss -ltn`); the servers read `PORT` (API, default 8787), `WEB_PORT` (Vite, default 5173) and `API_URL` (where Vite proxies `/api`).
   - Full stack: `PORT=<port> npm run cf:dev` serves the built app and the real Worker on one origin.
   - Each state: `npm run mock` with `npm run dev`, and the mock's switches: `DELAY_MS=1500` holds Loading and Saving on screen, `FAIL_SAVES=1` makes every save end as "not saved" with Retry, `FAIL_FIRST_SAVE=1` loses one reply, and stopping the mock shows the stale state.
   - Stop `cf:dev` with Ctrl-C, or from a script with SIGINT to its process group (`kill -INT -<pgid>`), and wait until its port is closed: it runs workerd in a separate process, so killing npm alone leaves the port held.
   - A script that types then presses Enter must wait for the button to enable first: Add is disabled until the Model has the text, one frame after input, and Enter does nothing while it is disabled. Its local data lives in `cloudflare/.alchemy/`; delete that folder to reset.

   Completion: no sideways scroll at 390 px or at 320 px, and every state holds `arc-design`'s taste rules on screen (its words, the focus ring, hover, pressed and disabled, nothing moving under reduced motion), or the reply says `NOT_RUN` for the browser check.
10. **Deploy only when asked.** An app that isn't deployed still runs: `npm run cf:dev` serves it on this machine and keeps its data in `cloudflare/.alchemy/`. Say that, and say that a list read returns the newest 200 rows. A deploy creates a public URL, so confirm first, and say before confirming that the template's API has no sign-in: anyone with the URL can read and write. Follow [references/deploy.md](references/deploy.md). Completion: `npm run api:check -- <deployed-url>` passes, and the reply gives the URL and the destroy command.
11. **Report** through `arc-html-response`, ending with its packet. The checks are each step's Completion line above. An app with no commits has no revision: write `revision unknown`. Completion: every check is labelled `PASS`, `FAIL` or `NOT_RUN`.

## Pins

`package-lock.json` pins every version; install with `npm ci` and commit the lockfile. `package.json` pins `foldkit` 0.171.0 exactly, `effect` to `~4.1.4`, `@foldkit/vite-plugin` 0.29.1 and `alchemy` 2.0.0-beta.87. Foldkit and Alchemy are pre-1.0, and Foldkit's peer range is `effect ~4.1`. Don't raise a pin as a side effect of other work. Effect here is v4: most examples online are v3 and won't compile, so read `node_modules/effect/ai-docs` instead of answering from memory. Foldkit's API is in its type files: `node_modules/foldkit/dist/**/*.d.ts` (for example `dist/test/scene.d.ts`).

## Maintaining this skill

After changing the template, run `bash <skill-dir>/tests/test-template.sh`. It copies the template to a temp folder, runs `npm ci`, the checks, the build and the static render, lints the static page, and runs the API check against the mock. It needs the network.
