# Realtime

A live connection here is one WebSocket per open page, to a room the server holds. In Foldkit the socket is a Subscription, which is a stream of Messages from outside the app. Sending is a Command. Every frame is decoded with a Schema before it becomes a Message, and every connection state has its own screen.

This skill builds level 4 of `arc-design`'s pyramid and starts from `arc-web-production`'s template. [overlay/](overlay) is a working example on the template's notes app: a note added by one person shows for everyone, each person sees how many are connected, the socket reconnects with backoff and catches up, and two pages open a WebRTC data channel through the same socket. Copy from it. This skill builds the app side and says what the server must do. Where that server runs is `arc-system-architecture`'s decision.

## Steps

1. **Give the socket a reason.** The template already reloads its list every 5 seconds, and a poll is the right tool for data that changes every few minutes. A socket earns its place in three cases: another person's change must show within about a second, the screen shows who is connected right now, or two browsers need a handshake for WebRTC. Completion: one sentence names what must arrive live and which case it is. If none fits, say the poll is enough and stay at level 2.
2. **Start from a passing baseline.** Do `arc-web-production`'s steps 1 and 2 for the app, then `bash <skill-dir>/scripts/apply-overlay.sh <app-dir>`. It copies the overlay, pins the two packages the mock needs, and adds the realtime test and stylesheet to the package scripts. It replaces eight template files and stops if the app has changed one of them. In that case, copy the new files and merge the additions marked `arc-realtime` by hand. Completion: `npm run check` passes before you change anything.
3. **Say what the server must do, and hand the placement on.** The app needs a server that holds connections open, with one object per room that sees every socket in it. The template's stack already has one, its Durable Object. Anything else is a placement question, such as a different platform, a TURN server or a media server. Name the need and send it to `arc-system-architecture`. Completion: the reply states the need in one sentence and chooses no platform.
4. **Design the connection states before the screen.** Read [references/client-rules.md](references/client-rules.md) now. It holds the file shape, the state machine, the rules for the Subscription, the Commands, catch-up and tests, and the pitfalls. Completion: the connection is a tagged union with a case for connecting, live, reconnecting and offline. Every frame type has a Schema and a past-tense Message. One failure Message takes every frame that does not decode.
5. **Write the room twice.** Read [references/server.md](references/server.md) now. It holds the frame protocol, the Worker on the hibernation API, the mock, its switches, and what ran where. Put every frame check in `cloudflare/room.ts`, which both servers import. The server never trusts a frame. It checks each one, mints peer ids itself, and stores a write frame through the same idempotent insert as `POST`. Completion: `npm run api:check -- <url>` passes against `npm run mock` and against `npm run cf:dev`, and `cf:dev` was stopped with SIGINT and its port is closed.
6. **Write the client.** The socket is a Subscription that runs while the Model wants one. Sending is a Command through a service, so a test can swap in a stub. Writes stay on the template's HTTP path, so a dropped socket never loses one. Completion: `update` reads no clock and no randomness, and the backoff wait is a Command that answers with a Message. The welcome frame starts a list load, so a reconnect catches up. The last good data stays on screen while not live.
7. **Add WebRTC only when two browsers must talk directly.** Read [references/webrtc.md](references/webrtc.md) first. It says what the overlay proves (a data channel between two pages on one machine), what is unverified (camera and microphone, STUN, TURN, a media server), and what to check in Cloudflare's Realtime docs. Completion: the reply labels the data channel `PASS`, `FAIL` or `NOT_RUN`, labels media and TURN `NOT_RUN` unless you ran them, and sends the TURN or media server to `arc-system-architecture`.
8. **Apply the look.** Read `arc-design`'s "The look", "Taste rules" and "Motion" sections and follow them. Don't run its routing steps, which send you back here. Realtime styles live in `src/realtime.css`. Each connection state has its own `@keyframes` name and its own sentence, counts use tabular figures, and the status never relies on colour alone. Completion: `npm run lint:styles` passes for `styles.css` and `realtime.css`.
9. **Test without a browser.** Story tests for `update` through every connection state and a reconnect, Scene tests for each state's screen, the socket stream and each send Command against stub services, and direct `update` calls for a welcome that arrives during a list load. Completion: `npm run check` passes, and one wrong expectation, in a temporary copy of a test file, was seen to fail.
10. **Test with two people in a real browser.** `npm install --save-exact --save-dev playwright-core@1.65.1`, then run `test/two-people.browser.mjs` as its header says, against `npm run mock` with `npm run dev` and against `npm run cf:dev`. Adapt its expectations to your app. Completion: it passes, or the reply says `NOT_RUN` and why. It must show a change crossing from one person to the other with no list request, presence counting both, and a drop that recovers and catches up.
11. **Look at every state.** `npm run mock` with `npm run dev`, at 390 px and at desktop width, in light and dark. The mock's switches hold each state on screen: `DELAY_MS` for connecting, `REFUSE_SOCKETS=1` for reconnecting and then offline, `DROP_SOCKET_AFTER_MS` for a drop and a recovery, and stopping the mock for stale. Completion: no sideways scroll at 390 px and each state shows its own words, or the reply says `NOT_RUN` for this check.
12. **Report** through `arc-html-response`, ending with its packet. Completion: every check is labelled `PASS`, `FAIL` or `NOT_RUN`, in three groups: what ran against the mock, what ran against local workerd, and what ran against a deployed Worker. A deploy is `arc-web-production`'s step 10, and it is `NOT_RUN` until someone asks for it.

## Pins

`scripts/apply-overlay.sh` holds the versions. `ws` is 8.23.0 and `@types/ws` is 8.18.2, both exact and both devDependencies. The mock needs a WebSocket server and Node has none built in. A hand-written frame parser would be code to keep correct that the app never ships. Those two versions are already in the template's lockfile through other packages, so the install downloads nothing new. `playwright-core` is 1.65.1 for the two-person test, installed only when that test runs. It drives a browser you already have through `CHROME_PATH`. The browser's `WebSocket` and `RTCPeerConnection` and Node's own `WebSocket` client need no package. Don't raise a pin as a side effect of other work, and never raise one of the template's pins.

## Maintaining this skill

After changing the overlay, or after the template changes, run `TMPDIR=<a folder with room> bash <skill-dir>/tests/test-overlay.sh`. It copies the current template, applies the overlay, and runs typecheck, tests, a wrong expectation that must fail, the style lint, the build, the API check against the mock and against local workerd, and the two-person browser test against both. It needs the network and prints `SKIP` for the browser steps when no Chromium is found. Its first step fails when the template has changed a file the overlay replaces. Merge that change into the overlay's copy, then refresh `overlay-base.sha256` as the comment in the test says. A deployed Worker, camera and microphone, and a TURN server are not covered by it.
